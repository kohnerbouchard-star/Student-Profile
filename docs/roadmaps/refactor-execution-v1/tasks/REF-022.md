# REF-022 — Move Staff ledger adjustment behind the existing atomic command

Status: IN_PROGRESS. Risk: R3. Dependencies: REF-021. Maps to ARCH-205/ARCH-300.

## Read first

`backend/src/domains/economy/api/staffLedgerAdjustmentHttpHandler.ts`, Economy application/infrastructure, the exact adjustment RPC and current Admin/economic invariant tests. Read `backend/src/platform/supabase/adminMutation.ts` where the existing command uses it.

## Allowed change

One Staff adjustment application/repository seam plus injection/tests. Proposed application target if absent: `economy/application/adjustLedgerForAuthorizedStaff.ts`. No new RPC, account type, currency conversion, manual balance update, amount validation policy or migration. Budget: ten meaningful files.

## Implementation

1. Freeze permission/game/player/account checks, amount representation, reason/audit fields, currency, request identity and exact RPC arguments/results.
2. Put HTTP-independent orchestration behind an Economy-owned application function and raw invocation behind its existing repository/atomic-command adapter.
3. Keep the command a single authoritative database transaction. Do not implement adjustment with `.update(balance)`, append a separate compensating ledger entry or use a second service-client write.
4. Preserve the existing idempotency key/fingerprint, replay receipt and error mapping. Do not round earlier, accept a different sign convention or silently default missing currency.
5. Test allowed credit/debit cases, invalid precision/currency/account, wrong Staff/game, insufficient funds if the current contract applies, repeated key, conflicting payload, transaction failure and concurrency.

## Acceptance and validation

The HTTP handler no longer owns its raw adjustment call. Every successful request creates the same authoritative ledger/audit effects; denied/failed requests create none; retries cannot adjust twice. Run backend `test:economic-ledger-invariants`, `test:player-banking-public`, `test:admin-api`, root `test:admin-economic-writes`, focused disposable-database race/replay tests and shared gates.

## Stop / rollback

Any need to alter SQL/grants/rounding becomes a separately authorized corrective ticket. Revert the source seam without reverting later security fixes. Never delete ledger rows or change production balances as rollback.
