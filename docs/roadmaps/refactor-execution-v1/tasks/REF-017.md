# REF-017 — Extract Player roster persistence into its existing owner

Status: VERIFIED_COMPLETE. Risk: R2. Dependencies: REF-016. Maps to ARCH-100/ARCH-401. Recheck #668 ownership.

## Read first

`backend/src/domains/players/api/playerRosterHttpHandler.ts`, its current tests/callers, Players application/infrastructure contracts, public index and response-privacy tests. Determine which operations are reads before selecting the edit scope.

## Allowed change

Only roster-read persistence and its approved application adapter; proposed `players/contracts/playerRosterReadRepository.ts` and `players/infrastructure/supabasePlayerRosterReadRepository.ts` if no equivalent exists. Keep create/enroll/archive/reset operations unchanged. Budget: ten meaningful files.

## Implementation

1. Freeze the selected read's query predicates, projected fields, sorting, pagination, totals and empty/unknown-game behavior. Identify the current Staff/Player audience and privacy boundary.
2. Reuse or extract a minimal repository port taking the existing server-derived scoped context and read filters. Project database column names and UUIDs only inside infrastructure where appropriate.
3. Move the current query literally, preserving predicates and error mapping; inject the repository from the existing composition root rather than constructing a global Supabase client in the handler.
4. Leave the HTTP adapter responsible for method/auth/input/response translation. Preserve context reference identity and do not add a new general-purpose Players service.
5. Test repository failure, empty roster, another game's records, duplicate display names, paging boundaries and private credential/UUID exclusion.

## Acceptance and validation

The selected handler has no direct roster persistence; the query/result contract and call count are unchanged. Mutating roster actions remain owned by their original application commands. Run existing roster/Players tests through their current registration, backend `test:player-security`, `test:player-request-scope`, `test:admin-api`, `typecheck:all` and privacy/architecture checks.

## Stop / rollback

If reads and writes cannot be separated within the budget, split before editing. Do not introduce a permissive query that filters game scope in JavaScript. Revert the port/injection/move together; no data migration is required.
