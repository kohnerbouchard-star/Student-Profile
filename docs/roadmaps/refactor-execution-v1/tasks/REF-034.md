# REF-034 — Converge Story notification delivery through the existing transaction boundary

Status: PLANNED. Risk: R3. Dependencies: REF-033. Maps to ARCH-402/ARCH-602.

## Read first

Story effect executor/repository, `backend/src/domains/notifications/infrastructure/supabasePlayerStoryDeliveryRepository.ts`, notification application/contracts, `playerStoryDeliveryHttpHandler.ts`, delivery/privacy tests and any existing notification outbox/transaction SQL.

## Allowed change

One Story-to-Notifications semantic contract and its exact adapter/imports/tests. Proposed narrow public export under Notifications only when absent. No new queue/outbox, retention policy, recipient model, delivery channel, SQL transaction or realtime protocol. Budget: twelve meaningful files.

## Implementation

1. Determine whether notification creation is already part of the Story transaction or occurs through an existing post-commit delivery mechanism. Record that boundary and every deduplication key.
2. Expose the owner-approved notification intent/receipt contract and remove only the selected deep infrastructure coupling.
3. Preserve existing atomicity: a notification inserted in the same SQL transaction stays there; a post-commit outbox remains the same outbox. Do not replace either with an unreliable fire-and-forget JavaScript call.
4. Preserve game/player/participant scope, visibility, delivery order, read/unread state and replay handling. Keep private Story payloads out of public notification fields.
5. Test duplicate execution, rollback, delayed delivery, recipient mismatch, missing optional Story content and repeated acknowledgement using current fixtures.

## Acceptance and validation

Exactly the same intended recipients and one logical delivery per existing deduplication contract; no lost or duplicate delivery from the new boundary. No cross-game/private payload leakage. Run backend `test:player-notifications`, `test:world-runtime`, Player `notifications-inbox`, `story-delivery`, focused Story transaction tests and shared gates.

## Stop / rollback

Stop if the change would alter SQL ownership/atomicity or needs infrastructure provisioning. Record that dependency separately. Revert only TypeScript contracts/adapters, not delivered messages or read state.
