# REF-009 — Replace Contract reward-issuance forwarding without splitting its transaction

Status: PLANNED. Risk: R3. Dependencies: REF-008. Maps to ARCH-208/ARCH-300.

## Read first

`admin-api/gameRoutes.ts` `rewardMatch`; Contracts Staff reward-issuance handler; the actual reward RPC/repository and ledger/audit receipt tests. Read applied SQL for understanding only. Do not infer command names from old roadmaps.

## Allowed change

The POST `/games/:game/contracts/:contract/progress/:progress/rewards/issue` adapter and the smallest existing Contracts application/repository seam. Proposed translator: `admin-api/contractRewardIssueOperation.ts`. Focused tests and exact owning test registration are permitted. No SQL/migration or reward-formula changes. Budget: ten meaningful files.

## Implementation

1. Identify the exact atomic transaction that validates eligibility, locks progress, issues rewards and writes ledger/audit/idempotency evidence. Record its arguments and outcome mapping.
2. Reuse that transaction through a narrow Contracts command; pass server-derived context and the existing idempotency identity without generating a fresh key on retry.
3. Replace only this route's Classroom fetch. Preserve authorization, game/contract/progress association, downstream denial behavior, status/error envelope and audit fields.
4. Keep replay response semantics and exact monetary/currency precision. Do not call Banking then Inventory then Progression separately; a cleaner interface must still invoke one authoritative settlement boundary.
5. Compare authoritative effect counts before/after, including a failure injected after validation and a concurrent double-submit case in a disposable environment.

## Acceptance and validation

One successful issuance produces exactly the existing ledger, inventory/reward and audit effects; identical retries reuse the result; conflicting replay and concurrent duplicate attempts never duplicate rewards. Denied/failed commands leave no partial state. Run Contract lifecycle/acceptance, backend `test:economic-ledger-invariants`, `test:admin-api`, root `test:admin-economic-writes`, and affected database/race acceptance plus shared gates.

## Stop / rollback

Stop if preserving atomicity requires SQL changes; open a separately authorized forward-migration ticket instead. Revert only the source adapter. Never compensate by deleting ledger rows or modifying issued rewards in production.
