## Allowed change

Only the legacy Settings save/error lifecycle and its explicit adapter/tests. Proposed helper if needed: `admin/settings-save-controller.js`. V2 code is a reference, not blanket edit permission. No form redesign, settings defaults, difficulty/payroll/attendance formula, backend schema or generated bundle changes. Budget: eight meaningful files.

## Implementation

1. Verify whether the legacy bridge is loaded and what responses it intercepts. An unused file becomes a REF-015 candidate, not a reason to add new runtime wiring.
2. Identify the Settings source controller's existing save promise and connect success/failure handling there instead of globally rewriting fetch or observing unrelated DOM mutations.
3. Preserve exact request shape, selected-game context, idempotency/CSRF headers, validation messages, no-op handling and saved-state semantics.
4. Give the controller explicit listener disposal and stale-response rejection when the active game or route changes. Keep user's in-progress form values on server rejection.
5. Remove only the now-redundant Settings interception. Preserve normal number defaults and accessibility/focus fallbacks unless individually proven obsolete.

## Acceptance and validation

Invalid timezone/settings, wrong-game denial, offline/unavailable service, double save and route remount retain expected behavior and do not post duplicates. A failed save never shows a success state. Run Settings browser/unit cases, `npm run test:admin-v2`, `test:admin-local-mutation-ui`, backend `test:game-sessions`, and asset/interaction/architecture checks.

## Stop / rollback

Stop if fixing a pre-existing Settings bug would change product behavior; record a separate correction. Revert only the source/controller changes and matched script reference. Do not alter global defaults or retained backend compatibility DTOs.
