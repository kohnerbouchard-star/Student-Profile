# REF-018 — Extract Staff Attendance persistence while preserving one reward transaction

Status: PLANNED. Risk: R3. Dependencies: REF-016. Maps to ARCH-208/ARCH-401. Respect the existing context/Attendance owner.

## Read first

`backend/src/domains/attendance/application/recordAttendanceForAuthorizedStaff.ts`, `api/staffAttendanceScanHttpHandler.ts`, `api/attendanceRewardPolicy.ts`, existing Staff application context and Attendance mutation/RPC tests. Inspect the actual transaction before moving any call.

## Allowed change

The Staff attendance-record application persistence seam and one injected repository. Proposed `attendance/contracts/attendanceRecordRepository.ts` and `attendance/infrastructure/supabaseAttendanceRecordRepository.ts` if needed. No Player clock-in change yet, reward formula, timezone policy, SQL or scanner UI edits. Budget: twelve meaningful files.

## Implementation

1. Record the exact Staff/player/game checks, policy reads, transaction arguments, idempotency identity and audit/reward outcome of the current operation.
2. Extract database-specific reads/RPC invocation into Attendance infrastructure behind a narrow contract. Keep pure policy decisions in their existing owner and inject the repository at composition.
3. Preserve the single existing attendance/reward/ledger transaction. Do not create a separate Economy transfer after an attendance insert or duplicate a reward request across domains.
4. Propagate the approved context unchanged to the application/repository boundary; derive database IDs from that context, not scanner body identity.
5. Characterize on-time/late/repeated scans, missing player, wrong game/Staff, paused game, invalid policy and transaction failure. Include duplicate and concurrent scans.

## Acceptance and validation

The application no longer performs its selected raw persistence call; equivalent input yields the same attendance record, amount/currency, audit and replay receipt. Failure cannot leave attendance rewarded twice or partially posted. Run backend `test:admin-local-mutations`, `test:player-security`, `test:economic-ledger-invariants`, `test:admin-api`, focused Attendance/race tests and root economic/architecture checks.

## Stop / rollback

Stop if atomicity or established context semantics would change. A needed SQL correction is separate forward-migration work. Revert the repository extraction/injection only; never delete or rewrite attendance/ledger data as rollback.
