# REF-035 — Extract one Messaging thread lifecycle use case

Status: PLANNED. Risk: R2. Dependencies: REF-006, REF-016. Maps to ARCH-401/ARCH-402.

## Read first

`backend/src/domains/messaging/api/playerMessageThreadLifecycleHttpHandler.ts`, route/parser tests and current Messaging policy/create-thread SQL. At the observed main the handler calls `read_player_message_policy_v1` for policy GET and `create_player_message_thread_atomic_v1` for thread creation.

## Allowed change

The create-thread application/repository path only. Proposed `messaging/application/createPlayerMessageThread.ts` and `messaging/infrastructure/supabasePlayerMessageThreadRepository.ts` if absent. Leave policy GET in its existing path unless a shared pure normalizer is required. No send/NPC auto-reply/retention/moderation redesign or SQL changes. Budget: ten meaningful files.

## Implementation

1. Preserve early method/route checks, rejected runner-secret header, prohibition on query parameters and server-derived Player scope.
2. Retain current create parsing: recipient public identifier, title/body limits, forbidden raw UUIDs and body/header idempotency-key agreement. Parsing stays side-effect-free.
3. Extract a use case invoking the same `create_player_message_thread_atomic_v1` RPC once, with unchanged game/player/recipient/title/body/key arguments.
4. Keep the existing result mapping: applied outcome returns 201, replay returns 200; preserve private/no-store responses and safe error translation. Do not create a separate message insert after thread creation.
5. Test wrong recipient/game, invalid fields, conflicting keys, query parameters, unavailable RPC, duplicate creation and context/session failure.

## Acceptance and validation

The create branch no longer contains raw RPC persistence; policy GET and all existing browser contracts are unchanged. One logical request creates one atomic thread/initial message outcome. Run backend `test:player-messaging`, `test:player-security`, `test:player-request-scope`, Player `messaging-connected`, full typecheck/smoke and architecture/privacy guards.

## Stop / rollback

An NPC reply feature request is separate work, not justification to broaden this extraction. Revert use-case/repository injection only; preserve message history and retention controls.
