# REF-029 — Extract one Contract repository read-projection family

Status: VERIFIED_COMPLETE (bounded repository seam only). Risk: R2. Dependencies: REF-007, REF-008, REF-009, REF-028. Maps to ARCH-401.

## Read first

The current `contracts/infrastructure/supabaseContractRepository.ts` and its large test file, public/staff read repositories and the REF-007–009 use cases. Verify current file size and call graph; a large test alone is not justification to split production code.

## Allowed change

One cohesive read family, preferably progress/submission projection, extracted within Contracts infrastructure with its exact callers/tests. Proposed target: `contracts/infrastructure/contractProgressReadProjection.ts` only if that is the observed owner. No mutation transaction, public API, whole-domain folder move or broad test reformat. Budget: ten meaningful files.

## Implementation

1. Select the smallest read projection that has identifiable inputs/outputs and independent tests. Record all callers, query dependencies and public/private DTO mappings before choosing a destination.
2. Extract the existing query/projection helpers without changing joins, filters, order, limits, null handling or numeric serialization. Keep side-effectful review/reward operations in their existing owner.
3. Inject/reuse the same repository/client/context rather than creating independent queries per row. Preserve the existing public repository interface unless a caller-specific internal seam suffices.
4. Move only directly related tests; retain lifecycle and negative cases in the owning suite. Do not split test files merely to lower an oversized-file metric.
5. Compare baseline and extracted output/query traces for empty, large, mixed-state and wrong-game fixtures; ensure no additional network/database fan-out.

## Acceptance and validation

The selected production responsibility becomes independently reviewable, with unchanged runtime behavior and no duplicate implementation. Record actual production/test line changes separately. Run backend Contract acceptance/lifecycle, Admin API, focused repository tests, Player Contracts flows, full typecheck/smoke and architecture checks.

## Stop / rollback

Stop if no cohesive production seam exists or the extraction would distribute one transaction across files with changed behavior. Verification-only disposition is valid. Revert the helper and caller wiring together; no database changes.
