# REF-028 — Separate Contract availability policy from persistence

Status: PLANNED. Risk: R2. Dependencies: REF-016. Maps to ARCH-208/ARCH-401.

## Read first

`backend/src/domains/contracts/services/playerContractAvailabilityService.ts`, its current callers/tests, Contract public-list/acceptance contracts, scoped repositories and optional Story availability inputs.

## Allowed change

Availability-input persistence and a pure policy boundary inside Contracts. Proposed repository target if necessary: `contracts/infrastructure/supabaseContractAvailabilityReadRepository.ts`; use the current policy module if one exists. No contract status/reward/targeting rules, gameplay defaults, SQL or UI changes. Budget: ten meaningful files.

## Implementation

1. Enumerate every availability input and current precedence: game state, player eligibility, accepted/completed state, deadlines, visibility, limits and any optional Story projection.
2. Move direct queries out of the service into a scoped repository. Pass an explicit immutable input record into the policy calculation, with the existing clock/timezone supplied rather than hidden global reads.
3. Preserve evaluation order and existing error-versus-unavailable distinctions. Do not replace an absent optional Story projection with a new mandatory dependency or remove its valid fallback.
4. Keep public reason codes and action gating identical for list, detail and accept consumers. Do not compute a second authoritative eligibility rule in the browser.
5. Test before/at/after deadlines, missing optional data, paused game, already accepted/completed, wrong player/game and failed repository reads.

## Acceptance and validation

Availability policy runs without database access for supplied inputs; infrastructure retains exact game/player filters and query count. Same fixtures produce the same eligibility/reason/response. Run backend Contract acceptance/lifecycle and Player security suites, Player `contracts-public`, `contracts-connected`, `contracts-submit`, `story-decisions`, typecheck/smoke and architecture checks.

## Stop / rollback

If a discovered inconsistency requires changing eligibility semantics, record a separate product/bug ticket. Revert the extraction/injection only. Do not broaden visibility or bypass current eligibility to make fixtures pass.
