# REF-010 — Replace Player access-code-reset forwarding

Status: PLANNED. Risk: R3. Dependencies: REF-005. Maps to ARCH-100/ARCH-400. Activation waits for resolved #668/#736 ownership and an accepted auth baseline.

## Read first

`admin-api/gameRoutes.ts` `accessResetMatch`; `backend/src/domains/players/api/playerAccessCodeResetHttpHandler.ts`; current credential hashing/access-code/reset repository and session-revocation tests; Admin security guard and REF-004 fixture.

## Allowed change

Only POST `/games/:game/players/:player/access-code/reset`, its proposed local `admin-api/playerAccessCodeResetOperation.ts`, a minimal existing Players reset use-case extraction and tests. No login algorithm, key selection, token/cookie model, new reset policy or password/MFA edits. Budget: ten meaningful files.

## Implementation

1. Characterize reset authentication, Staff capability, selected-game ownership, player lookup, secret generation/hash storage, revocation behavior and response privacy.
2. Reuse the existing server-owned reset command. Move any necessary non-HTTP logic out of the old handler without changing its randomness, hashing, expiry or audit semantics.
3. Invoke it from the guarded Admin path with validated context; never pass a service-role key as an end-user bearer or trust a body-provided player/game identity.
4. Replace only the reset proxy call. Preserve request/idempotency identity, retry/conflict behavior and the exact approved response exposure; no secrets enter logs, fixtures or browser fields beyond the already-approved contract.
5. Assert the existing code/session validity behavior before and after reset, including another game's player, a revoked Staff session and a failed persistence operation.

## Acceptance and validation

Equivalent requests produce equivalent authorization, reset/revocation/audit outcomes; the route makes no Classroom network call. Failed/denied resets do not rotate credentials. Run backend `test:player-security`, `test:player-request-scope`, `test:admin-api`, relevant reset tests, root `test:auth-boundaries`, `test:web-session-release` and shared checks. Authorized staging auth evidence is required before release.

## Stop / rollback

Stop on unresolved auth incidents, collision or changed credential semantics. Revert only this adapter; retain later accepted security fixes. Never restore old credentials or invalidate real users as a test/rollback step.
