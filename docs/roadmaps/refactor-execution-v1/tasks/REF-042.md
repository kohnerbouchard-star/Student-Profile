## Allowed change

Inventory use/redemption post-write invalidation only and its existing shared data-plane integration/tests. No optimistic economic writes, new polling, global cache flush, unrelated feature migration, API or CSS changes. Budget: ten meaningful files.

## Implementation

1. Record exactly which resources current Inventory actions invalidate/refetch and at what point the server receipt is accepted.
2. Replace duplicated page-specific refresh calls with the existing explicit invalidation mechanism; keep one owner for this action's resource list.
3. Preserve request idempotency and mutation serialization. Invalidate only after an authoritative applied/replayed success according to the existing contract; rejected/aborted actions must not manufacture inventory changes.
4. Deduplicate overlapping realtime and mutation refreshes without suppressing required authoritative reads. Carry session-generation checks so an old action cannot invalidate a new session.
5. Test successful use/redemption, replay, rejection, double click, route remount, concurrent realtime event, slow/out-of-order read and logout during mutation.

## Acceptance and validation

One logical action causes the same authoritative visible state with no duplicate mutation or increased refresh fan-out. Draft form/focus behavior remains intact. Run Player `inventory-read`, `inventory-redemption-connected`, `mutation-control-regressions`, `read-ordering`, `realtime`, `route-refresh`, `recovery`, `verify` and shared guards.

## Stop / rollback

Stop if the change requires redesigning global realtime/cache behavior or loosening freshness tests. Revert Inventory's invalidation mapping/wiring only. Never alter server balances/holdings optimistically to conceal a missing refetch.
