## Options requiring owner selection

The already-approved baseline is modular-monolith hardening with existing domain owners, same-origin Admin/Player BFFs, server-derived context and atomic economic authority. Keeping that baseline is not a new architecture choice. A framework rewrite or microservices conversion would require a separate proposal and is not recommended for these blockers.

| Decision | Options and tradeoff | Recommendation, NOT approval |
| --- | --- | --- |
| **D1 — Player freshness mechanism** | A: a small shared session/resource-generation coordinator at existing read-publication boundaries; bounded change, but every participating writer must honor it. B: converge the selected flows onto one session-owned API/cache instance; potentially cleaner ownership, but broader lifecycle/caller changes and still needs ordering guards. C: adopt a new state/query library; migration scope beyond this repair. | Start with A if it can cover terminal, action-flow and realtime publication completely. Choose B if current seams make A incomplete or more complex. Prove the adversarial race either way; abort alone and flow-only refresh substitution are insufficient. |
| **D2 — Borrower and operator model** | A: retain current player-borrower/legacy eligibility semantics behind explicit contracts; lowest immediate change, mismatch remains documented. B: explicitly distinguish personal and business borrowing, using canonical mandate checks for business operators and a compatibility path for existing loans. C: replace all lending with a generalized borrower engine; largest policy/migration scope. | B as the target, phased through a separately approved semantic change. Borrower liability is not the same as permission to operate; shareholding alone must not silently become management authority. No new ledger, automatic liability transfer or cross-currency aggregation is implied. |
| **D3 — Isolated Markets calculations** | A: retain tested inactive code and explicitly amend the refactor outcome. B: select and integrate a real production consumer under separate feature ownership. C: remove only after an explicit owner feature-retirement decision. | A for now; preserve future scope and report the original outcome accurately. No deferral/removal/completion label is authorized by this recommendation. |
| **D4 — Legacy retirement** | A: migrate and qualify one responsibility/candidate at a time. B: coordinated legacy-shell cutover after full caller, parity and retained-client evidence; broader deployment risk. Immediate unproven deletion is not an acceptable option. | A; preserve useful compatibility until its individual retirement gate closes. |
