## Authorization semantics

Dispatch inputs travel through environment variables and quoted Bash comparisons, never GitHub-expression interpolation into shell source. The protected `production` job compares the exact requested SHA to the run SHA, fetches authoritative `refs/heads/main` through the fixed GitHub API endpoint, and only then emits `approved_commit`. Repository, event, main ref, action and origin must all match; malformed/unavailable lookups fail closed without logging the response or token. A rerun requires a new dispatch and approval.

Every downstream side-effect job consumes the protected job's exact SHA output. The production verifier rechecks current main immediately before each POST, including after every retry delay. Status publishers also recheck and target only that approved SHA. The original 72-attempt bound, 10-second delay, request timeouts, 15-minute job timeout and controlled-response validation remain unchanged. Read-main failures do not retry automatically or permit a POST. If main advances after a pending status, publication stops rather than reporting stale success; the pending commit status may remain, with the failed Actions run providing the rejection evidence. A fresh separately approved dispatch is required.

These are immediate authoritative freshness checks, not an atomic GitHub-main/production transaction or a cross-workflow merge lock. Any future authorized probe needs a coordinated no-merge observation window; this patch neither grants that window nor alters main merge policy. Protected-environment enforcement must be verified independently before any later live dispatch; a YAML environment name alone does not prove required-reviewer/no-bypass settings.

The live endpoint is deliberately not invoked here. Its BFF can cause nonce claim/expiry cleanup; it is not represented as database-effect-free. Canonical-origin convergence remains a separate #735 prerequisite for useful production verification. Existing origin constants are unchanged.

## Sole-operator recovery authority proposal — REVIEW ONLY

The owner has explicitly selected a one-person operating model: Kohner Bouchard acts as the external system administrator and confirms each recovery himself. This explicitly supersedes the earlier unselected Entra/two-person proposal in this document. No Microsoft tenant is assumed, no second recovery approver is required, and no in-app/game role becomes an authority. This is sole control with compensating authentication and audit controls, not dual control. Existing engineering-review requirements and release holds are not removed.

### Minimal external identity setup

Propose one small dedicated operations console and broker, outside Econovaria's application authentication system, using a maintained WebAuthn implementation rather than bespoke cryptography. A workforce IdP, GitHub login and an approval tenant are unnecessary for this one principal. Pin the exact HTTPS origin and RP ID to the dedicated operator hostname; no wildcard origins, parent-domain credential scope, embedded frames, shared game cookies or application SSO. Store the operator's immutable external principal and explicitly enrolled credential public keys in the broker's private identity registry, not in a game-admin permission row. Public registration, email/password reset, email magic links, SMS/TOTP fallback, and game-role-to-operator promotion are absent.

Proposed physical setup: one daily-use FIDO2 hardware security key plus two independently enrolled backup keys, one kept securely apart and one off-site under the same owner's control. Each uses local PIN or biometric user verification. Do not clone a TOTP seed or store all backups beside the daily key. Keep bootstrap/key inventory and non-secret recovery instructions separately. Enrollment must verify the chosen hardware's characteristics and attestations as applicable; a client-side attachment hint alone is not proof of hardware protection. This proposal chooses device-bound, non-syncing operator credentials; it makes no claim of formal AAL3 certification.

Bootstrap and any key addition/removal require a separately reviewed setup ceremony. There is no bootstrap token, credential registration, new persistent account or infrastructure configuration in this PR.

### Fresh exact-operation confirmation and one-use authority

The broker resolves the target server-side to its immutable Auth identity and fixed staging project `eecvbssdvarfcykcfrny`. Show the operator an unambiguous public target reference and known account identity, exact action, specific existing factor set proposed for retirement, session-revocation consequences, reason and identity-evidence reference. The operator verifies identity using evidence independent of the compromised account/session or a requester's control of email. Independent evidence does not mean a second person; it remains a real verification requirement, not a self-asserted boolean.

Create a canonical request containing target, project, operation, exact factor IDs/state version, evidence reference, source commit, executor digest, policy version, request ID, audience and expiry. Bind a fresh server-generated WebAuthn challenge to that request digest and the current operator session. Require `userVerification=required`, check the signature, expected challenge, exact origin/RP ID, presence and verification flags, registered credential status and server-side expiry. Proposed challenge lifetime: two minutes. Require a new ceremony for every recovery, even after console login; editing the target/action/factors invalidates the challenge. Explicit confirmation and a typed target are error-prevention measures, never authentication by themselves. WebAuthn binds the assertion to the challenge; the broker must correctly bind that challenge to the displayed canonical request. A normal security key does not itself display the target for confirmation.

For the simplest deployment the same broker verifies and orchestrates, so an opaque server-side grant suffices; a bespoke signed-token service is unnecessary. Proposed initiation-grant lifetime: 60 seconds, one request, one operator session, one fixed staging executor. Consume it using durable compare-and-set before any provider effect, then use the existing exact-request/state-machine one-shot acquisitions. Do not restore a consumed grant after timeout or ambiguous outcomes. Recheck operator credential revocation, current target state, source/executor identity and expiry at acquisition. A changed source or target requires a new confirmation. Preserve the separate existing recovery-attempt expiry of at most 15 minutes; a short initiation grant is not a reusable session-wide administrator privilege. Queue delays never extend authorization.

Keep provider authority exclusively in the reviewed broker/executor, not the browser or a general CI job. This remains a future credential-binding prerequisite, not a claim that provider API keys are intrinsically scoped to one target. GitHub may remain source/CI only; if a future workflow executor is chosen, OIDC authenticates that workload and never substitutes for fresh human WebAuthn approval. Any existing environment reviewer/self-review/bypass policy that conflicts with sole operation needs a separate explicit policy decision; this proposal changes none.

### Restriction, revocation and compulsory re-enrollment

Before retiring any factor, durably restrict the exact target in all application authorization paths, record the recovery attempt and queue its notification. Preserve `mfa_required=true`. Revoke and verify old provider refresh sessions and application/BFF sessions, invalidate applicable outstanding reset/recovery grants, and enforce fresh server-side session/security state. Provider sign-out does not by itself immediately invalidate every already-issued access JWT; session-ID or security-version checks and the existing application restriction must reject those tokens. Verification cannot be a successful HTTP status alone. Provider revocation ambiguity stops factor retirement and keeps the target restricted.

Only the exact approved factor set may be retired; newly changed provider factor state requires new approval. Restrict the enrollment ceremony to this request and its user-bound provider session/grant. Require enrollment and verification of new primary and separately retained backup factors recorded specifically for this attempt, followed by user-private password setting when applicable. Arbitrary AAL2, merely having two factors, or deleting the old factors is not completion. The operator never receives the user's new password or factor secrets. Keep existing one-shot reservation/completion and unsafe-restart protections. At completion consume the recovery grant, revoke recovery sessions and require a fresh normal sign-in with the replacement factors. Expiry, cancellation, uncertain effects and failed delivery do not restore ordinary access.

This preserves the existing scope's distinction: it restricts Econovaria access; it does not falsely promise that a browser-visible Supabase Auth bearer cannot call Supabase's public Auth API. The reviewed adapters must prove the exact effect and restriction guarantees before execution is enabled.

### Audit and notification

Durably record the operator's immutable principal, credential identifier/fingerprint, fresh-authentication time, canonical request digest, target reference, reason/evidence reference, source/policy/executor identities, one-use consumption, each acquired provider phase, outcomes, denials and notice acknowledgements. Send sanitized copies to an append-only/tamper-evident log outside game-admin control; define retention/access before live use. No passwords, tokens, private keys, QR seeds or delivery grants in logs. No log-sink or signing/storage credential is created here.

Queue notifications to the target's pre-existing verified contact and the operator's security contact at initiation and completion, and for failures, cancellation and authenticator changes. Do not let the request substitute its notification recipient. Notifications contain no authorization capability. Missing delivery acknowledgement remains visible and must not silently count as completion. Operator access is never recovered through the notification mailbox.

### Recovering the sole operator's own access

Loss of the daily key: use an already enrolled backup with the same fresh WebAuthn/PIN-or-biometric requirements, revoke the missing credential, invalidate old operator sessions and unconsumed grants, and enroll/test a replacement and retained backup before routine operations resume. This is another enrolled authenticator, not an MFA bypass. The off-site key supplies a separately held last-resort authenticator; no second person needs to approve its use. Using the external operator key to recover the same person's Econovaria account is permitted; using the locked Econovaria account to recover operator authority is not.

Loss of every operator key: no email-only, SMS-only, domain-control-only, typed-code-only or application-admin reset. Stop recovery operations. A separately approved infrastructure re-bootstrap may be considered only with an independently retained phishing-resistant infrastructure authenticator and the documented owner/bootstrap record, invalidating all previous operator credentials/sessions/grants and re-enrolling primary/backups. Such infrastructure access is not assumed to exist. Its own recovery chain must not collapse to email-only proof. Without that independent trust anchor, the operator console remains locked; there is no safe automatic fallback. Public-key registry/configuration backups restore state, not proof of identity. This availability trade-off must be accepted before live enablement.
